## `packages/core/tsconfig.build.json`

> 9 lines

**What it is.** The nine lines that produce a distributable engine. Same base, same strictness, three
different answers from the checking config next to it:


- **`rootDir: "src"` with `include: ["src/**/*.ts"]`** means `dist/` mirrors `src/` one-to-one: `dist/index.js`
  and `dist/index.d.ts` are the package's entry points, and `dist/qr/render.js` sits where `src/qr/render.ts`
  was. A build that changed that shape would silently break any consumer importing a subpath.
- **`outDir: "dist"`** — the same directory `.gitignore` ignores, which is the point: it is reproducible
  from `npm run build:core` and belongs to nobody's commit.
- **`module: "ESNext"`** is redundant with the base file *on purpose*. The one thing this config must never
  inherit is a CommonJS emit, because `packages/core/package.json` says `"type": "module"` and a CommonJS
  `.js` inside an ESM package is a hard runtime error. Stating it here means a future change to the base
  file cannot quietly break the published output — a build config is exactly the place where a redundant
  setting earns its line.

The inherited `declaration: true` and `sourceMap: true` are what make the output usable rather than merely
loadable: `.d.ts` files so a TypeScript consumer needs no special handling, and source maps so a stack trace
inside the built engine points at the file a reader of this document is looking at.

**Every line**

```json

4 │     "rootDir": "src",
5 │     "outDir": "dist",
```

## `packages/core/vitest.config.ts`

> 10 lines

**What it is.** Ten lines describing how the engine's tests run — and the two timeouts in it are the reason
this file exists at all rather than the defaults being accepted.


- **`globals: true`** makes `describe`, `it` and `expect` available without an import, which is the style
  the engine's 81 tests are written in. It is a deliberate choice over the more explicit alternative: the
  tests here are long and dense (a fountain decode, a 300-frame transfer), and an import line at the top of
  each of them earns nothing.
- **`include: ['test/**/*.test.ts']`** — only `*.test.ts`. The directory also holds probing scripts used
  during development; naming a file without the `.test` suffix is how you keep it out of the suite without
  moving it.
- **`testTimeout` and `hookTimeout` at 120 s** are the interesting pair. The default 5 s is unusable for
  this codebase: `transfer-e2e.test.ts` drives complete transfers of multi-kilobyte payloads through
  hundreds of simulated camera frames, `fountain.test.ts` solves linear systems over GF(2) for recovery
  curves, and the QR tests rasterise and decode real symbols. On a slow machine the honest runtime of a
  single one of those tests is tens of seconds; a 5 s limit would produce intermittent failures that look
  like algorithm bugs and are actually scheduling noise.

The trade is explicit: a genuine infinite loop in this suite fails after two minutes instead of five
seconds. That is the correct direction for tests whose subject is "does this converge?" — and `npm test`
still finishes in well under a minute on the development machine, because the timeout is a ceiling and not
a duration.

**Every line**

```ts
 5 │     globals: true,
```

## `tools/diag/degree-experiment.ts`

> 220 lines

**What it is.** The experiment that chose the fountain code's tuning constants — the degree
distribution (`c = 0.03`, `delta = 0.5`) and the frame schedule (a systematic prefix followed by the
LT stream). It is one of the four scripts wired to an npm script (`npm run diag:degree`), and its
output is archived verbatim in `docs/degree-experiment-output.txt` and quoted as a table in
`docs/ALGORITHMS.md` §2.3 and `docs/ARCHITECTURE.md` §6.

**The metric, restated because everything here depends on it.** Every row reports
*frames the sender must display per source block*, `sent/K`. That unit is chosen deliberately: a
transfer happens at a fixed frame rate on a screen, so `sent/K = 1.10` means "the sender must show
about 10 % more frames than the file has blocks, therefore about 10 % more seconds". Overhead in
*bytes* would be a proxy for that; overhead in *frames* is the transfer time itself.

**What this script does not do, on purpose.** There is no QR rendering, no camera, no image
processing and no compression anywhere in the file. The encoder and the decoder are driven directly,
in-process, and the channel is modelled as "the camera did or did not capture this frame". That
isolation is the point: the `diag:core` and `diag:web` scripts prove the pixels work end to end, and
this script exists to answer one question that pixels would only obscure — *given that a camera
captures roughly this many of the frames on screen, which degree distribution needs the fewest of
them?* Modelling the loss rate by hand instead of filming a screen makes the sweep run in ~30
seconds and makes its result reproducible on any machine, which matters because the constants it
chooses are baked into the protocol.

**The comparison matrix.** Nine configurations, times two schedules, times three channels:

| axis | values |
| --- | --- |
| degree distribution | robust soliton `c = 0.03` (shipped), robust soliton `c = 0.10`, ideal soliton, ideal soliton with a denser fallback, uniform (control) |
| schedule | `lt` — pure fountain stream, no systematic prefix; `sys+lt` — the `K` systematic frames first, then the fountain stream |
| channel | `keep = 1.0` (perfect optics); `keep = 0.7` (one frame in three lost); `keep = 0.5` with bursts of 40 lost frames every 60 |

The last row of the matrix is the one that makes it a *sweep* rather than a demo: a channel with
only independent frame loss flatters both the systematic prefix and the ideal soliton, because the
loss is spread evenly. Real loss is bursty — a hand crosses in front of the camera, the autofocus
hunts, the sender's screen dims for a moment — and a burst removes a *contiguous* run of frames,
which is exactly the pattern that an uncoded prefix recovers from worst.

**`Config` and `Result`.** `Config` is what a row of the matrix is: a label, a schedule, the
`DegreeOptions` handed to both the encoder and the decoder, and the two knobs of the decoder's dense
fallback (`denseLimit`, `stallThreshold`). The trailing `maxFrames` is deliberately optional and is
set on exactly one configuration; that field has its own paragraph below, because it is a scar from a
bug this file produced. `Result` is what one run reports: frames sent, frames received, frames per
block, the redundant-frame counter, how many times the dense fallback fired and how big its matrix
was, wall-clock milliseconds, and whether the transfer completed at all.

**`randomPayload(length, seed)`.** The payload is random bytes driven from a seeded RNG, not a text
file or a logo. The reason is that the metric must not be flattered by the payload: a highly
compressible payload would make the *later* compression stage shrink the file, change the block
count, and turn "frames per block" into a measurement of the payload's entropy. Random bytes fix the
block count at exactly `k` and make every run of the same seed comparable to every other.

**`runOnce(...)` — one simulated transfer.** The encoder is constructed with the session's payload,
`k`, block size, session id and degree options; the decoder is constructed with the same numbers and
*the same degree options*, because that is the actual protocol property under test: the receiver
never receives a distribution along with a frame, it recomputes the frame's neighbours from
`(seed, k, sessionId)`. If the two sides disagreed about the distribution, nothing would decode at
all, and that is a property of the shipped `fountain/lt.ts`, not of this script.

The channel model is eight lines. `keep` is an independent per-frame coin flip; the burst model sits
on top of it: every sixtieth frame starts a run of `burst` consecutive losses. A dropped frame
`continue`s without touching the decoder, which is the whole reason the protocol can survive a loss
— no retransmission, no acknowledgement, no ordering.

A caught frame is fed to `decoder.addFrame(frame, encoder.encode(frame))` and the loop asks
`decoder.isComplete` after every one; the moment it flips, the run returns the frame count it took.
`sent` is computed as `frame - firstFrame + 1` rather than as the loop counter, and `firstFrame` is
`k + 1` for the LT-only schedule: the encoder's first `k` frames are the systematic prefix, so a
sender that is not using the prefix must start at the frame after them. Counting from the wrong
origin was not a cosmetic bug — with the loop starting at 0 for both schedules, every `lt` row was
credited with `k` frames it never displayed, and the `lt` column looked *better* than the shipped
schedule in exactly the channel where the prefix matters most.

**The frame budget, and the second bug behind it.** The budget is read from `LB_MAX_FRAMES`, else the
configuration's own `maxFrames`, else `12k + 2000`, and it is added to `firstFrame` — it counts
*frames the sender displays*, not absolute frame indices. That distinction is the second scar in this
file: with the budget used directly as an absolute index cap, a leash of 400 frames on a schedule
whose first displayed frame is `k + 1 = 1025` meant the loop body never ran. The uniform row printed
`sent/K = -0.610` — a *negative* cost, at 0 % complete — which is the way a bounded run tells you it
did nothing at all: `maxFrames - firstFrame` with the sign of an empty loop. Both the negative number
and the wrong-origin count are the kind of error a benchmark can hide indefinitely, because a
benchmark has no assertion to fail; the archive only looks wrong if a human reads the column and
notices that zero cost is not a plausible answer.

**The uniform control, and why it wears a leash.** The uniform distribution draws each frame's
neighbours from the whole file, so a frame XORs about `k/2` blocks and a decoder solve is two orders
of magnitude slower than the shipped distribution. It is in the matrix as a control — the textbook
worst case, measured rather than asserted — and its rows therefore read `sent/K = 0.391` (400 frames —
"the leash") with `recv/K` falling from 0.391 to 0.271 at 30 % loss to 0.111 in the bursty channel, all
at `0 %` complete. The sender never finished inside its budget, and that *is* the finding: the row is
not a slow transfer, it is a demonstration that half the file per frame is not a coding scheme. The `maxFrames: 400` field on that one configuration is the fix from the paragraph above; without it the
sweep spends minutes of CPU proving what the row already says. It takes priority over `LB_MAX_FRAMES`,
which is deliberate: that variable raises the budget for a longer, more careful run, and if it also
raised the leash then asking for more trials would re-introduce the very wait the leash exists to
prevent.

**`average(...)` and the trial seeds.** Each cell runs `LB_TRIALS` (default 3, 5 for the archived run)
independent trials with seeds `1000 + t * 17`, and reports means. The seed stride is not decorative:
consecutive seeds would give trials with correlated frames, and a mean over correlated trials is not a
mean. Note what is *not* averaged: `completeRatio` is reported as a fraction, so a cell that never
finished cannot masquerade as a fast one — the archived run's uniform rows print `0 %`, which is the
honest answer, while a genuine 100 % is printed for every other row.

distribution *shape* (`mean degree`, `P(1)`, `P(2)`, `P(3)`, `P(4)`) for the robust and ideal
variants. The shape summary is what turns the timing result into an explanation; the archived run

30 % loss, 3.594 against 3.838 in the bursty channel), which is why it is the shipped constant. The
dense fallback's two rows are identical to the plain ideal rows in every channel — a denser
Gaussian-elimination threshold does not rescue a distribution whose tail is empty, it only spends
CPU earlier.

The prefix trade is visible in the same table: the systematic prefix *costs* 0.006 frames per block on
a perfect channel (1.096 → 1.102, half a percent) and saves 0.034 at 30 % loss and 0.236 in the
bursty channel. It is worth its frames under loss and nearly free without, which is the argument for
shipping it.

**Honest limits of this experiment.** The loss model is a coin flip plus bursts, not a camera: it does
not model blur, partial symbols, motion smear, or the error-correction headroom that makes a *partly*
readable frame either readable or not. The `ms` column is decoder CPU time on the machine that ran
it, not screen time, and it is in the table only to show that the shipped configuration is not
paying a decode cost for its lower overhead. Compression is off, so the numbers describe the
fountain layer alone. What the sweep establishes is a *relative* ordering of distributions under
loss models that are optimistic about a real handheld camera — and the ordering is what the constants
needed; the absolute end-to-end rate is measured by `diag:core`, `diag:web` and the mobile app, not
here.

**Reproducing it.** `LB_K`, `LB_TRIALS` and `LB_MAX_FRAMES` override the block count, the trials per
cell and the frame budget. `LB_TRIALS=5 npx tsx tools/diag/degree-experiment.ts` reproduces the
archived run in about 30 seconds; the archive's own header repeats that command.

The cheap variant is `LB_TRIALS=3 LB_MAX_FRAMES=6000`, which finishes in 21 seconds on the same

instructive way. The shipped-configuration rows agree: 1.094 vs 1.096 (`lt`) and 1.103 vs 1.102
(`sys+lt`) clean, 1.559 vs 1.554 at 30 % loss, 3.649 vs 3.594 in the bursty channel. The ideal-soliton
rows do not: 2.498 against 2.059 clean, 3.136 against 2.572 at 30 % loss, and in the bursty channel
the 3-trial run is still only 67 % complete when it hits the 6000-frame cap. That spread is not noise
in the harness, it is the ideal distribution's tail showing itself from the outside: a handful of
high-degree frames dominate both the frame count and the wall-clock time (the clean-channel `ms` column

quantity is unstable. The robust distribution's own spike at P(1) is precisely what removes that
instability — which is a second, independent argument for shipping it, and the reason the archived run
uses 5 trials rather than 3.

## `tools/diag/prefix-experiment.ts`

> 59 lines

**What it is.** The experiment that chose the systematic prefix length — how many of the `k` source blocks are
sent, in order, before the fountain stream starts. It is one of the two scripts wired to an npm script
(`npm run diag:prefix`), and its output is archived in `docs/prefix-experiment-output.txt` and quoted as a
table in `packages/core/src/fountain/lt.ts`.

**The metric, stated in the header:** *"frames-sent per block (the quantity that maps directly to transfer
time)"*. Frames per block is the right unit because the transfer happens at a fixed frame rate on a screen:
`sent/K` of 1.106 means the sender must display 10.6 % more frames than the file has blocks, which is 10.6 %
more seconds. Overhead in bytes would be a proxy for that; overhead in frames *is* the time.

**The sweep, and the channel model.**


Three channels, each of which corresponds to something a user does with a phone: a perfectly still setup
(`keep = 1.0`), one frame in three lost to blur or motion (`keep = 0.7`), and half the frames lost plus
regular bursts (`keep = 0.5, burst = 40`) — the burst model is explicit about what it stands for:


Every sixtieth frame begins a run of forty consecutive lost frames. That is a hand crossing the camera, an
autofocus hunt, or the moment the person holding the phone breathes out. A channel model with only
independent per-frame loss would have flattered long prefixes; the burst model is what makes the *real* cost
of a full systematic prefix visible, because a burst knocks out a *contiguous run* of systematic frames —
which leaves exactly the specific holes that a uniformly-covering LT frame is bad at filling.

**`prefix/K` is swept in six steps from `0` to `1.0`, and it is passed to both sides.**


Both sides must agree, because the prefix is structural rather than signalled: slots `0 .. prefix-1` carry
the source blocks in order, slot `prefix` carries a mask frame that makes the prefix invertible, and only
then do the LT slots begin (see `packages/core/src/fountain/lt.ts`). A receiver that assumed a different
prefix length would read the LT stream at the wrong offsets, so the value is a session parameter derived
from `k` — never transmitted, never guessed.

`Math.max(1, …)` keeps the sweep meaningful at `0` (no prefix at all, pure LT) without producing a zero-length
prefix for tiny `k`; in production `defaultSystematicPrefix(k)` returns 0 for small `k` anyway, because a
prefix costs more than it saves when the file is only a handful of blocks.

**The measured table, which is also the comment above `defaultSystematicPrefix()`:**


The reading of that table is the project's clearest example of a decision made by measurement rather than
intuition. `0.00` (pure LT) is competitive but never best; `1.00` (a full systematic pass) is *optimal on a
clean channel* — exactly 1.000 frames per block, one frame per block, and a receiver sees the file arrive in
order — and the worst option once frames are being lost. `0.10` is best or statistically tied in every
column. The reason a short prefix captures both ends is in the `lt.ts` comment: the first ~10 % of blocks
arrive at exactly one frame each, so a receiver has verified data on screen within seconds (which the app
uses for a partial preview of a received image), while the LT tail keeps its near-loss-optimal efficiency.

**The script is reproducible with one command per column.**


`LB_K` (default 1024), `LB_TRIALS` (default 3) and `BLOCK = 512` are the knobs; the archive records the
command, and re-running it on the development machine reproduces every cell to three decimals — the numbers
in the shipped comment are not a memory of a run but a run that can be repeated. The multi-`k` behaviour is
worth knowing about when reading the archive: `1.000` for a full prefix on a clean channel is a *ceiling*
(you cannot do better than one frame per block), and the `k = 64` column is noticeably noisier than
`k = 1024` because the same three trials cover fewer independent events — which is why the chosen default is
stated against the `k = 1024` column and not against the small ones.

## `tools/diag/verify-roundtrip.ts`

> 37 lines

**What it is.** The script that found a correctness bug of the worst possible kind: transfers that reported
*complete* and then produced the wrong bytes. One line of comment states the purpose — *"Isolates a suspected
correctness bug: bytes differ after isComplete === true."* — and the rest of the file is a 200-trial
brute-force search for it, kept in the repository as the instrument that can re-demonstrate the failure if
the fix is ever doubted.

**The shape of the experiment: many independent payloads, byte-exact comparison, no shortcuts.**


- **200 trials** rather than one, because the bug was intermittent: it depended on which equations the
  decoder happened to solve, which depends on the session's mask and therefore on the session id. A single
  trial would have shown nothing on most runs.
- **`sessionId = 1 + trial` and a payload seed derived from the trial** give every iteration a different
  symbol schedule *and* different bytes. Varying only one of the two would have missed the interaction
  between the mask block (which depends on the session id) and the data.
- **5000 bytes in blocks of 512** gives `k = 10` — small enough to finish in milliseconds, large enough for
  the solver to have real work to do and therefore a real chance of hitting the aliasing case.
- **Random payload bytes**, not a counter pattern: a counter would make some differences invisible after a
  masked XOR, which is exactly the kind of difference the bug produced.

**The loop that drives the transfer is deliberately minimal.**


It plays frames in order with no packet loss, because loss was not the variable under investigation; `k * 6`
is a generous cap that stops a non-converging session from hanging the script. The `incomplete` bucket exists
so that a genuine convergence failure is *not* counted as a mismatch — three distinct outcomes (`ok`, `bad`,
`incomplete`) is the difference between "the code is wrong" and "the code is slow", and conflating them would
have sent the investigation in the wrong direction.

**The reporting is built for the moment of failure, not for a summary.**


Four things are printed for the first three failures, and each was chosen to discriminate between hypotheses
without a second run:

- **`firstDiff` and its block index** — which of the ten blocks is wrong, and whether it is the first
  (suggesting a systematic-prefix problem) or a later one (suggesting the LT solver).
- **`solved = n/10` and `dense`** — how the decoder got there, so a failure that only appears through the
  dense fallback is visibly different from one that appears during peeling.
- **The first four bytes of the wrong block versus the right one** — the pattern of the difference is the
  fingerprint. An all-zero result says a block was never written; a plausible-looking but different block
  says it was written from the wrong equation.
- **The `(enc as any).prefix` cast** — the script reaches into private fields (`prefix`, `mask`, `maskData`,
  and later `solveVariable`, which it wraps). Two scripts in this directory do that, and the casts are left
  in place rather than cleaned up: an instrument that can see inside the object under investigation is the
  point, and these fields were not public API at the time.

**What it found.** The self-XOR aliasing in `drainReady`: a block that had just been *solved* was still
listened to by an equation that had already used it, so a later solve could XOR the block into itself and
zero it out — producing a "complete" reconstruction containing zeros where data should be. The permanent
form of this finding is the regression test in `packages/core/test/fountain.test.ts`, and the note in
`packages/core/src/fountain/lt.ts` explaining why the ready-list must be drained before a block is solved. The
final line of the script — `ok=… bad=… incomplete=…` — is what a fix looks like: `bad=0` with `ok=200`.

## `tools/diag/debug-frame.ts`

> 42 lines

**What it is.** A single-session, frame-by-frame trace written during the hunt for the receiver bug that
`verify-roundtrip.ts` searched for statistically. Where that script runs two hundred random sessions looking
for *any* failure, this one replays **one** failing session with an instrument attached, and it is kept
because it answers a different question: not "does it happen?" but "which frame does it happen on, and what
does the decoder believe at that moment?"

**The session is deterministic, and that is the point.**


Payload, session id and mask are all derived from constants, so the trace is identical on every run — which
is what makes it a usable record. A failing case that can only be reproduced "sometimes" cannot be debugged
by reading output; a failing case pinned by three numbers can be re-examined as many times as necessary, and
the fix can be checked by re-running exactly the same file.

Note `k = Math.ceil(payloadLength / blockSize)` — ten blocks of 512 bytes for 5 000 bytes, the last one
partial. That partial block is deliberate: an off-by-one in the tail handling would only appear there.

**Three things are printed before a single frame is sent, and each one eliminates a hypothesis.**


The prefix lengths must match (they are derived from `k` on both sides and never transmitted), and the mask
block must be identical on both sides — it is *derived* from the session id rather than sent, which is what
makes the systematic prefix invertible without spending a frame on it. Printing the first four bytes of all
three masks turns "the two sides disagree about the session" from a suspicion into a fact stamped at the top
of the log.

**The instrument: wrapping the decoder's solve function.**


Every solve is logged with the block's first four bytes **and whether the whole value is zero**. That second
field is the fingerprint the bug produced: when a block is XOR-aliased into itself during `drainReady`, the
result is a block that is solved, marked done, and contains zeros. A trace where `allZero=true` appears on a
block mid-transfer is a smoking gun; a trace without it rules the aliasing out and sends you looking
elsewhere. This is the difference between a script that prints state and a script that prints *the
discriminating* state.

**The frame loop prints the slot layout explicitly, because the slot layout is the thing under suspicion.**

another. The `seed === 3` line prints the derived LT seed (`seed - prefix - 1`) — the mapping from a display

## `tools/diag/lt-diag.ts`

> 46 lines

**What it is.** A short, self-contained check that the systematic prefix is an optimisation and not a
requirement. Its header is the finding: *"Establishes that the prefix is a latency optimisation and never a
correctness requirement: the decoder completes whether or not the prefix is present, it just needs fewer
frames when it is."*

This matters more than it sounds, because it is the property that lets the app *start sending immediately*.
If the LT tail could not reconstruct the file on its own, then a receiver that joined late — or one that
missed the prefix during the seconds the sender was still being aimed — would be stuck forever, and the
prefix would be a single point of failure. `lt-diag.ts` is the evidence that it is not.

**The switch that removes the prefix is a seed offset, and that is the whole trick.**


Slots `0 .. prefix-1` hold the systematic frames and slot `prefix` holds the mask frame, so any seed `> k`
is unambiguously in the LT region — starting at `k + 1` skips *all* of the prefix regardless of how long it
is. Note the consequence for the comparison: the two arms of the experiment do not send the same frames, by
construction, and the question being asked is not "which is faster" (that is
`tools/diag/prefix-experiment.ts`) but "does the LT-only arm still finish at all".

**`run()` measures one thing beyond completion: how the frames were used.**


The four-way tally is what turns "it finished" into a diagnosis. `redundant` counts frames that arrived after
their information was already known — the normal and unavoidable overhead of a fountain code — and `dup`
counts frames the decoder had literally seen before (a frame displayed twice, or the same slot read twice).
A run where `dup` grows and `accepted` stalls is a symptom of a channel repeating itself; a run where
`redundant` dominates is the price of the code's tail. Both are invisible in a simple "complete: true".

The result object is printed as JSON per configuration, which is why the four lines per `k` can be diffed
between runs:


**`buildDegreeDistribution(K)` is called once per run for its description, not for its behaviour** — the
encoder and decoder pick their distribution from their own defaults. Printing `meanDegree` alongside the
results is what lets a reader connect a row to the distribution that produced it (8.23 at `k = 256`, 10.57 at
`k = 1024`, the numbers quoted in `docs/ALGORITHMS.md`).

**The experiment's four lines per size** — systematic on/off × `keep = 1.0/0.7` — are the minimum needed to
make the claim. Two of them (prefix present) are the control, and two (LT only) are the claim; `keep = 0.7`
appears in both arms because the interesting question is whether the *lossy* LT-only arm still converges, and
a clean-channel-only experiment could not tell a robust code from a lucky one.

One honest caveat about the file, visible in its first line: it is labelled a historical diagnostic and is
not maintained. It is kept because the property it demonstrates — "the prefix is latency, not correctness" —
is the kind of thing that gets quietly broken by a well-meaning optimisation, and having a script that
re-establishes it in seconds is cheaper than re-deriving the argument from first principles.

## `tools/diag/diag.mjs`

> 31 lines

**What it is.** The first script ever run in this project, kept as documentation of a question that had to be
answered before anything else could be designed: *does the QR encoder produce symbols that a real decoder can
read?* Its header states both the question and what the answer was used for:

> The first thing ever run in this project: encode a payload at several sizes and raster scales, decode every
> symbol with jsQR, and compare the bytes. It is what established the minimum usable `scale` and the maximum
> payload that decodes reliably at each size - both of which the browser app now uses directly.

**It imports the engine by deep path, on purpose.**


This is a `.mjs` file, so the engine modules are pulled in with dynamic `import()` and an explicit `.ts`
extension — the form `tsx` resolves directly from the TypeScript source with no build step. The script
therefore exercises the same code the browser bundle ships, which is the property that makes its conclusions
transferable; a version that imported a compiled copy could be testing something subtly different.

`encodeText` is imported and never used, a reminder that this file is a notebook page rather than a tool.
(Editing it to tidy the import would be harmless, but the value of the script is that it is exactly what was
run; the README's convention is to leave historical scripts alone.)

**`tryDecode` — the entire experiment in six lines.**


Encode → rasterise → decode with a *different* implementation → compare the bytes. Three details carry
weight:

- **`quietZone: 4`** is the four-module quiet zone the QR specification requires. Testing without it would
  have produced "decoding is unreliable" conclusions that had nothing to do with this project's code — the
  decoder needs the margin, and later work (the browser pages, the mobile sender) all use the same four
  modules.
- **The byte comparison goes through `JSON.stringify(Array.from(...))`** rather than a manual loop. It is not
  the fastest way to compare two byte arrays; it is the shortest way to compare two byte arrays *and* have a
  readable diff when they differ, which is what a notebook script needs.
- **The returned object records `mask` and `ec`**, not just success. When a symbol fails to decode, the mask
  pattern is the first thing to suspect and the EC level is the second, so both are captured at the moment
  the symbol exists instead of being recovered later.

**The first sweep — sizes against raster scales.**


The payload pattern is `i & 0xff` — every byte value appears, in order — which is deliberately the *worst
case* for a decoder that mishandles a bit pattern or an escape, and deliberately incompressible so that the
symbol sizes reported are real. Two scales are tested per size because the question is not only "does it
encode?" but "how many screen pixels per module are needed for a camera to read it?" — the number that
decides how large the sender's symbol must be drawn on a phone screen.

**The second sweep — the biggest symbol at the smallest scales.**


`2953` is exactly the byte-mode capacity of QR version 40 at error-correction level L, so this is the
largest symbol the standard allows — the boundary case where a mistake in the encoder's bit packing or in the
version-40 alignment-pattern placement shows up. `boostEcLevel: false` turns off a convenience the encoder
otherwise applies (raising the EC level when there is spare capacity, which shrinks the usable payload);
disabling it is what makes the test hit the ceiling instead of quietly using a smaller symbol with more
redundancy. The three scales bracket the interesting region: 2 px per module is the practical floor for a
camera at close range, 4 is comfortable.

**What the output is for.** Every line is a JSON object, so the run's results can be compared between
attempts — which is how "the minimum usable scale" became a number in this project rather than an opinion,
and why the same `quietZone: 4` and scale floor appear in the browser sender and in the tests. The script is
not maintained and is not part of `npm test`; it is kept because the answer it produced is still load-bearing
in shipped code.

 1 │ # Deploying LightBeam Web
 2 │ 
 3 │ LightBeam ships as a unified Node web server (`@lightbeam/server`) hosting the
 4 │ built React + Vite Progressive Web App (`@lightbeam/web`). File bytes and
 5 │ passphrases **never** pass through the server — transfers travel optically from
 6 │ one device's display to another device's browser camera, and once visited the
 7 │ PWA's Service Worker caches the app shell so it continues working offline.
 8 │ 
 9 │ ---
10 │ 
11 │ ## 0. Browser Camera Requirement: HTTPS
12 │ 
13 │ Browsers expose `navigator.mediaDevices.getUserMedia` only in **secure contexts**:
14 │ - `http://localhost:8787` or `http://127.0.0.1:8787` (local single-machine testing)
15 │ - Any `https://` origin (required when opening the Receiver page on a second device over Wi-Fi or the internet)
16 │ 
17 │ Use the included Caddy reverse proxy (`deploy/Caddyfile`) for automatic Let's Encrypt TLS on public domains or `tls internal` on isolated LANs.
18 │ 
19 │ ---
